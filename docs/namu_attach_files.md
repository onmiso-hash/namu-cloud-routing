# 첨부 파일 주고받기 — 나무 클라우드 몫 (완료 보고서)

**작업**: `namu-file-upload-download` · **상태**: 완료 (2026-08-07)
**작성**: 2026-08-08 — 만들어진 뒤에 쓴 문서다. "이렇게 만들 것이다"가 아니라
**"지금 무엇이 어떻게 도는가"**를 적는다.
**짝 문서**: 나무 본체(터미널) 몫은 `namu-agent/docs/attach_files.md`.
그릇·격리 원칙·티켓의 기본 규칙은 그쪽이 원본이고, 여기서는 되풀이하지 않는다.

> **왜 이 문서가 필요했나**
> 이 저장소의 문서에는 첨부 관련 내용이 한 줄도 없었다(2026-08-08 확인).
> 설계서 2판에는 **티켓이 한 글자도 없고**, 티켓 설계의 원문은 우리 기록 어디에도
> 남아 있지 않다 — 코드가 인용하는 "설계서 5-4절 / 6-2절 / 7절"을 다섯 그릇 전부에서
> 찾았으나 없었다. 지금 이 기능을 설명하는 것은 코드와 그 주석뿐이었다.

## 1. 클라우드 몫이 본체와 다른 점

| 항목 | 터미널(본체) | 클라우드(이 저장소) |
|---|---|---|
| 파일을 다루는 방법 | 회원 PC의 `~/.namu` 사본에 git 명령 | **GitHub API로 회원 저장소에 직접** |
| 올리기 도구의 입력 | 파일 경로 또는 글자 원문 | **글자 원문만** (경로 칸이 없다 — 2절) |
| 회원 화면 | 없음 | 홈페이지 기억 화면에 첨부 기록 표시(6절) |
| 티켓 주소 | 이 PC의 개인 주소 | 서비스 주소 |

도구 이름과 개수(일곱)는 양쪽이 같다. 크기 상한도 같은 환경변수, 같은 기본값을
쓴다 — 다르면 "여기서는 올라가는데 저기서는 안 올라간다"가 되기 때문이다.

## 2. 올리기 도구에 파일 경로 칸이 없는 이유

웹에서 붙는 AI에게는 **디스크 경로라는 것이 없다.** 그래서 이 서버의
`namu_upload_file`은 글자 원문 하나만 받는다. 파일로 이미 존재하는 것은 전부
올리기 티켓으로 간다.

이 결정에는 사고 이력이 있다. 도구 소개문이 "이 도구는 디스크에 있는 파일을
올린다"고 말하는데 정작 그 도구에 경로 칸이 없자, 파일을 든 AI가 넣을 칸을 못 찾고
**자기 작업공간에서 파일을 글자로 옮기기 시작했다.** 즉 느려지는 일이 우리 도구를
부르기 **전 단계**에서 벌어졌고, 칸을 없애는 것으로는 원리적으로 안 막혔다.
지금은 소개문이 이 서버의 실제 모습대로 말한다(`routing_server.py:92` 주석).

## 3. GitHub API로 파일을 다룬다 — 지켜야 할 네 가지

서버 복제본을 거치지 않는다. 복제본에 파일을 놓았다 지우면 그 삭제가 다음 push에
실려 GitHub에서도 사라지고, 지운 채로 두면 다음 갱신이 되살린다 — 둘 다 실측으로
재현됐다. 그래서 파일은 API로만 다루고 이 서버 디스크에는 남기지 않는다.

| 지킬 것 | 왜 |
|---|---|
| **받기는 raw 형식으로 요청한다** | 기본 응답은 1 MiB를 넘으면 오류가 아니라 **빈 내용을 조용히 준다.** 큰 파일이 말없이 0바이트가 된다 |
| **목록은 복제본이 아니라 API에 묻는다** | 복제본에 크기까지 물으면 빠진 파일 몸통이 전부 내려와 격리가 뚫린다. API 목록은 이름과 크기만 주고 몸통은 안 준다 |
| **올린 직후 최신화 표시를 지운다** | 안 지우면 서버 복제본이 그 커밋을 모른 채 뒤처지고, 다음 기억 저장이 밀린 상태로 올리려다 거부된다 |
| **지워도 완전히 사라지지 않는다** | git이 이력을 남긴다. 도구 설명문이 이 사실을 회원에게 알린다 |

## 4. 서버 복제본에도 격리를 건다

클라우드 서버는 회원마다 저장소 사본을 하나씩 들고 있다. 여기에 첨부가 쌓이면
1인당 용량이 금방 찬다. 그래서 사본을 만들 때 세 가지를 함께 건다.

1. **몸통 없는 부분 복제** — 파일 내용을 미리 안 받는다.
2. **첨부 폴더 제외** — 작업트리에 첨부를 안 펼친다.
3. **"몸통이 빠진 것은 정상"이라는 표시** — 이 표시가 없으면 git 정리 명령이
   사본을 손상으로 보고 망가뜨린다.

**토큰은 디스크에 안 남긴다.** 3번 표시를 저장소 주소째로 적으면 그 주소에 들어
있는 열쇠가 설정 파일에 영구히 적힌다. 그래서 주소를 적는 방식이 아니라 명령을
줄 때마다 넘기는 방식을 쓴다(`user_repo.py:305` `_promisor_url_args`).

## 5. 티켓 주소 — 한 문이 두 사람을 받는다

주소 세 개를 연다: `GET /u/<티켓>`(올리는 화면) · `POST /u/<티켓>`(파일이 들어오는
문) · `GET /d/<티켓>`(받기).

**`POST /u/`에는 두 종류가 들어온다** — 회원 브라우저의 폼과, AI가 자기
작업공간에서 던지는 `curl`이다. 서버는 둘을 **구분하지 않고 구분해서도 안 된다.**
구분하는 순간 "AI가 막혔을 때 회원이 같은 링크로 이어 올린다"는 흐름이 깨진다.

**누구를 들여보내나**

- 웹 로그인 상태인데 티켓 주인이 아니면 거절한다.
- 로그인 상태가 아니면 **티켓 번호 자체를 인증으로 인정한다** — `curl`에는 쿠키가
  없기 때문이다.

두 번째 줄은 완화이지 무결점이 아니다. 번호를 손에 넣은 사람은 들어올 수 있다.
그래서 번호를 로그에 통째로 안 남기고 만료를 짧게 잡는다(올리기 2시간·한 번,
받기 1시간). **이 맞바꿈은 의도적으로 받아들인 것이다.**

**AI의 `curl`이 막히는 경우가 있다.** claude.ai 쪽에서 우리 주소를 안 열어 준
상태면 403으로 튕긴다. 이때 **링크는 그대로 살아 있으므로 새로 만들면 안 되고**,
회원에게 그 링크를 건네 직접 올리게 하면 된다. 도구가 이 안내를 응답에 함께 담아
돌려준다.

**이 서버에 파일을 남기지 않는다.** 받은 파일은 저장소로 보낸 뒤 그 요청 안에서
사라진다. 큰 파일이 잠시 임시 파일로 흘러도 응답 전에 닫혀 지워진다.

## 6. 홈페이지 기억 화면의 첨부 기록

기억 화면 버튼이 넷에서 다섯으로 늘었다. 2판 설계에는 없던 요구이며, "어떤 파일이
어떤 경로로 올라가고 지워졌는지 화면에서 볼 수 있어야 한다"는 2026-08-07 결정이다.

- **파일 이름을 맨 앞에 세운다** — 이 화면을 보는 이유가 "무슨 파일이 있더라"이고,
  그 답은 요약문이 아니라 파일 이름이다.
- **크기는 기록에서만 읽는다** — 저장소에 물으면 격리가 뚫린다.
- **지운 파일도 남긴다** — 이 화면을 보는 이유의 절반이 "그 파일 어디 갔지"다.
- **지우기 단추는 없다** — 파일을 빼는 일과 기록을 지우는 일은 다르다.

## 7. 크기 상한 20 MiB — 실측값

2026-08-07 밤, 운영 서버에 실제 파일을 올려 쟀다(서버가 스스로 잰 초).

| 크기 | 올리는 데 걸린 시간 |
|---|---|
| 1 MiB | 9.5초 |
| 5 MiB | 8.0초 |
| 20 MiB | 14.7초 (그중 GitHub에 보내는 구간 9.9초) |

받기도 20 MiB가 15초에 내려왔고 바이트 하나까지 같았다.

**한계도 함께 적어 둔다.** 21 MiB를 보내면 이 상한이 먼저 거절하므로 **GitHub가
몇 MiB까지 받는지는 확인하지 못했다.** 상한을 올릴 일이 생기면 환경변수
`NAMU_ATTACH_MAX_BYTES`로 먼저 올려 재고 나서 기본값을 고칠 것. 올릴 때 볼 것
두 가지 — 이 API는 파일을 글자로 바꿔 실어 보내 요청이 1.33배가 되고, 그 사본이
서버 메모리에 함께 올라간다.

## 8. 겪은 사고 둘 (같은 자리를 다시 밟지 않도록)

**① 시험 663건 전부 통과인데 운영에서는 전부 죽었다.** 티켓으로 올린 파일이
크기와 상관없이 502로 죽었다. 원인은 시험의 저장 대역이 넘겨받은 장부 연결을 한
번도 쓰지 않았다는 것이다 — 운영 코드는 그 연결을 첫 줄에서 읽는다. **대역이
진짜보다 덜 하면, 덜 한 그 부분의 결함은 시험이 원리적으로 못 본다.** 같은 구멍이
받기 쪽에도 그대로 있었고 아직 안 눌러 봐서 안 드러났을 뿐이었다.

**② 원인이 우리 코드 밖에 있었다.** 웹 AI가 파일을 글자로 바꾸는 증상이 세 번
재현됐다. 매번 우리 저장소를 뒤져 진짜 결함을 하나씩 찾아냈고, 찾았다는 이유로
그것을 원인으로 단정했다. 실제 원인은 **웹이 여섯 시간 묵은 도구 설명을 쥐고
있었던 것**이었다. 5분이면 끝날 진단 — "네가 받은 설명을 그대로 보여 달라"고
묻는 것 — 을 네 번째에야 했다.

상세는 교훈 그릇에 있다(`namu_search(bowl='learnings', query='티켓')`).
