01요약

AI 안내원은 나무 클라우드 홈페이지 다섯 장(/·/start·/memory·/safety·/faq) 오른쪽 아래에 붙는 말풍선이다. 방문자가 글로 물으면, 서버는 회원용 안내 문서 7장을 미리 조각내 만들어 둔 말뭉치에서 질문과 맞는 대목을 낱말 점수로 찾아내고, 그 대목만을 근거로 Gemini 3.5 Flash-Lite에게 답을 짓게 한다. 로그인은 필요 없다 — 처음 온 사람이 쓰는 창구이기 때문이다.

이 보고서가 특히 자세히 다루는 것은 세 가지다. ① 검색을 무엇으로 하는가 — SQLite 색인을 쓰려다 실측에서 방향을 바꾼 이야기, ② 어떻게 안전하게 짓는가 — 모델이 없는 사실을 지어내거나 없는 링크를 만들지 못하게 막은 다섯 겹, ③ 오늘 이 문서를 쓰는 계기가 된 하루 한도 — Google의 진짜 한도를 실측해 코드 기본값을 고치고 그대로 배포한 절차.

02설계가 지키는 약속 넷

src/ask.py 맨 위에 적힌, 이 파일 전체를 관통하는 규칙이다. 아래 모든 절이 이 넷 중 하나를 지키기 위한 장치다.

  1. 열쇠가 없으면 아무 일도 하지 않는다. NAMU_ASK_API_KEY가 비어 있으면 말풍선 단추 자체를 안 그린다 — 눌러도 답이 안 오는 단추보다 없는 편이 낫다.
  2. 말뭉치에서 못 찾으면 AI를 부르지 않는다. 검색 결과가 0건이면 그 자리에서 "모른다"고 답한다. 부르지 않으니 지어낼 여지가 아예 없고, 하루 요청 수도 쓰지 않는다.
  3. 근거 링크는 서버가 단다. 모델에게는 자료마다 매긴 번호만 말하게 하고, 그 번호를 우리 목록에 대조해 주소로 바꾼다. 모델이 주소를 지어낼 길이 없다.
  4. 실패해도 홈페이지는 멀쩡하다. 어떤 예외도 밖으로 새지 않고 부드러운 문구로 바뀐다. 무료 등급에는 가동률 약속이 없어 이 길이 드물지 않게 쓰인다.

03전체 흐름 — 여덟 단계

질문 하나가 답 하나가 되기까지 실제로 거치는 순서다(Guide.answer()의 처리 순서와 같다). 순서 자체가 설계 결정이다 — 예를 들어 "검색"이 "한도 세기"보다 앞에 있는 이유는, 부르지도 않을 질문으로 방문자의 하루치를 깎지 않기 위해서다.

05문서 → 조각 (수집·조각내기)

HTML에서 글자만 남기기

문서가 HTML이면 <script>·<nav>·<header>·<footer>를 통째로 버린다. 메뉴 글은 모든 문서에서 반복되므로 검색 결과를 오염시킨다. 대신 제목(h1~h6)은 # 표시로 남긴다 — 조각내기가 제목을 기준으로 자르고, 조각마다 "어느 문서 어느 대목"을 붙여야 근거 링크에 정확한 위치를 적을 수 있기 때문이다. 태그를 몽땅 지우면 8만 자짜리 글 한 덩어리가 되어 대목을 알 수 없게 된다.

제목 단위로 자르기

제목 경로(예: 2. 연결법 > 2-3. claude.ai에 붙이기)를 스택으로 쌓으며 문단을 가른다. 한 대목이 800자를 넘으면 문단 경계에서 다시 나누되, 조각 사이에 150자를 겹쳐 남긴다 — 문장이 정확히 조각 경계에서 잘려 앞뒤 맥락을 잃는 것을 막는다.

CHUNK_CHARS = 800자 OVERLAP_CHARS = 150자
// 문단이 하나뿐인데도 800자*2를 넘는 표·긴 목록만 예외적으로 글자 수로 자른다

뺄 대목도 지정할 수 있다 — 클라우드 사용 가이드의 "예전 모델(폐기됨)과의 차이" 절은 통째로 뺀다. 안내원이 그 절을 근거로 "지금 그렇다"고 답하면 방문자가 없는 기능을 찾아 헤매게 된다.

06검색 — 왜, 그리고 어떻게

방향 전환

처음에는 코어(namu-plugin/db.py)의 SQLite FTS5 세 글자 색인을 그대로 쓰기로 했다. 만들어 재보니 시험 질문 일곱 개 중 넷이 0건이었다 — "무료인가요" · "어떻게 시작하나요" · "기억이 어디 저장되나요" · "터미널에서도 되나요". 원인이 둘 겹쳤다.

  1. 세 글자 색인은 원리상 두 글자 낱말을 못 찾는데, 방문자가 실제로 쓰는 말이 '무료'·'가입'처럼 두 글자인 경우가 많다.
  2. 한국어는 낱말에 조사·어미가 붙는다. '무료인가요'라는 글자열은 문서 어디에도 없다 — 통째로 맞추는 방식은 이것을 '무료'로 이어 주지 못한다.

코어의 방식이 틀린 게 아니다. 코어는 회원이 손수 쓴 기억을 찾고, 안내원은 안내 문서를 자연스러운 질문 문장으로 찾는다 — 뒤쪽이 조사·어미를 훨씬 많이 달고 들어온다. 같은 도구가 두 자리에서 다르게 맞는 것뿐이다.

대신 택한 방식 — 색인 없이 그 자리에서 전부 훑기

말뭉치가 229조각·약 6만 7천 자이고 만드는 데 18밀리초라, 색인 없이 매 질문마다 조각 229개를 전부 점수 매겨도 비용이 거의 들지 않는다. 대신 세 가지 장치를 더했다.

① 꼬리를 떼며 찾기 — 조사·어미 문제 해결

실제 동작 — 긴 형태부터 한 글자씩 떼며 말뭉치에 있는 가장 긴 형태를 찾는다(최대 3글자)
방문자가 친 말시도 순서말뭉치에서 찾은 형태
무료인가요무료인가요 → 무료인가 → 무료인 → 무료무료 ✓
저장소가저장소가 → 저장소저장소 ✓
기억은기억은 → 기억기억 ✓

조사·어미 목록을 따로 관리하지 않는다 — 목록은 반드시 빠뜨리는 것이 생기고, 빠뜨린 것은 조용히 0건이 되어 아무도 모른다. _MAX_TRIM=3을 넘겨 더 떼면 asdfghjkl 같은 뜻 없는 글자도 우연히 'as' 같은 짧은 형태로 걸려 엉뚱한 조각이 근거처럼 인용됐다(실측으로 확인).

② 흔한 말은 약하게, 드문 말은 강하게

weight(낱말) = ln( 1 + 전체조각수 / (1 + 그낱말이나온조각수) )
// '기억'은 170회 나와 무게가 0에 가깝고, '무료'는 6회뿐이라 무게가 크다

③ 조각 점수 — BM25 계열 공식

score(조각) = Σ weight(t) × tf(t)×(k+1) / ( tf(t) + k×norm ) t∈matched norm = (1−b) + b × ( len(조각) / 평균길이 ) k = 1.2 (TF_SATURATION — 같은 말이 반복될수록 점수 증가폭이 완만해진다) b = 0.5 (LEN_NORMALIZE — 긴 조각이 낱말을 더 많이 품어 자동으로 이기는 것을 보정)
// 안 나누면 평균 215~505자로 벌어진 조각 길이 탓에 긴 문서가 검색을 독차지했다(실측)

④ 안전판 — 모르는 질문에는 억지로 채우지 않는다

질문의 뜻 있는 낱말 중 절반 이상이 말뭉치에 있어야 검색을 시도한다(_MIN_COVERAGE = 0.5). 점수만으로는 걸러지지 않는 경우가 있어 — "오늘 서울 날씨"의 '오늘'은 문서에 2회뿐이라 오히려 점수가 높게 나오지만, 뜻 있는 낱말 1개 중 0개만 맞아 0/1로 걸린다.

⑤ 제목도 함께 찾는다

본문뿐 아니라 제목까지 붙여서 낱말을 찾는다. 처음에는 본문만 봤더니 "claude.ai에 어떻게 붙이나요"가 「2-3. claude.ai에 붙이기」라는 대목을 못 찾았다 — 그 낱말이 제목에만 있었기 때문이다(실측). 제목은 그 대목이 무엇에 대한 것인지 가장 압축해 담은 줄이라, 오히려 본문보다 잘 맞는다.

07프롬프트 조립

10캐시와 한도

같은 질문 되풀이 막기

방문자(쿠키 또는 접속 주소)별로, 정규화한 질문 글자를 키로 최근 답을 최대 300건 메모리에 들고 있는다. 꽉 차면 오래된 것부터 3분의 1을 지운다. 같은 사람이 같은 질문을 다시 물으면 모델을 다시 부르지 않고 한도도 세지 않는다.

하루 한도 — 오늘 이 문서를 쓰게 된 계기

Google 무료 등급 자체 한도(분당 15 · 하루 500)에 닿기 전에 부드러운 문구로 먼저 안내하기 위해, 사이트가 스스로 더 낮은 한도를 건다. 2026-08-08 Google AI Studio 화면에서 실제 계정의 한도를 확인해, 추정치였던 기존 값을 실측값에 맞춰 이 문서 작성 직전에 v0.1.41로 올려 배포했다.

"한 사람"은 서명된 쿠키와 접속 주소(X-Forwarded-For 첫 값)를 각각 HMAC 지문으로 바꿔 세고, 둘 중 하나라도 한도를 넘으면 막는다. 접속 주소를 IP 그대로 적지 않는 이유는 소금 없는 지문을 쓰면 IPv4 42억 개를 전부 만들어 보고 원래 주소를 되찾을 수 있기 때문이다.

세는 시점은 모델을 부르기 직전이다 — 부른 뒤에 세면 실패를 일부러 되풀이해 한도를 무한히 우회할 수 있다. 세기 값은 NAMU_STORE_ROOT/ask/ask_counters.json 한 파일에 저장해 컨테이너가 다시 떠도 남는다(임시 파일에 쓰고 이름을 바꾸는 방식이라 쓰다가 죽어도 반쪽 파일이 안 남는다).

11요청 한 건의 전체 경로

  1. 브라우저 말풍선 스크립트가 POST /auth/ask에 {question, history}를 보낸다. 로그인 세션이 없어도 되는 유일한 POST 주소다.
  2. 본문 크기 검사 20KB를 넘으면 그 자리에서 거절 — 질문 500자 + 대화 3턴이면 넉넉하다.
  3. 방문자 식별 로그인 쿠키와 무관한 전용 쿠키(namu_ask_id, 30일)를 서명해 발급한다. 세기와 로그인 신원을 묶지 않는다.
  4. 스레드풀로 위임 ask.guide().answer(...)는 네트워크를 기다리므로, 여기서 그냥 부르면 그 1~2초 동안 서버 전체가 멎는다.
  5. Guide.answer() 실행 2~10절의 순서(길이 검사 → 캐시 → 검색 → 한도 → 호출 → 다듬기)를 그대로 밟는다.
  6. 항상 200 본문이 깨진 경우만 400이고, 그 밖의 모든 실패는 {"ok": false, "reason": ...}를 담아 200으로 돌려준다. 말풍선 하나 때문에 방문자가 오류 화면을 보면 안 된다.

  3. 03

  5. 05

  6. 06

  7. 07

14배포 구조

안내 문서 7장은 배포 이미지를 만들 때 통째로 굽는다(deploy/Dockerfile). 나무 본체 저장소(vendor/namu-agent)는 서브모듈로, 특정 커밋에 핀으로 고정돼 있다 — 실행 중에 문서를 다시 읽어 오지 않으므로, 문서를 바꾸려면 새 이미지를 만들어 다시 배포해야 한다.

오늘 한도 숫자(10·11절)를 바꾼 절차가 그 실제 예다: 코드 기본값을 고치고 → 저장소에 새 태그(v0.1.41)를 붙이고 → 이 저장소를 실제로 운영하는 onnamu-project 쪽 버전 핀 네 곳(docker-compose.yml·server_architecture_specs.md·deploy.yml의 --branch와 -t)을 맞춰 올리고 → 클라우드가 품은 나무 본체 엔진이 낡지 않았는지 자동 검사(check_cloud_core_pin.sh)를 통과한 뒤 → 푸시로 전체 재배포를 돌렸다.

참고

숫자만 바꿀 때는 이미지를 다시 만들지 않고도 배포 환경변수(NAMU_ASK_DAILY_CAP·NAMU_ASK_PER_PERSON)로 바로 올릴 수 있게 설계돼 있다. 이번에는 코드 기본값과 그 설명 주석을 실측값으로 함께 고치는 편을 택해 새 판을 정식으로 냈다.

16알려진 한계

  1. 접속 주소는 지어낼 수 있다. X-Forwarded-For는 방문자가 바꿔 보낼 수 있는 값이라, 주소를 바꿔 가며 부르는 것을 완전히 막지는 못한다 — 다만 쿠키 쪽 한도와 사이트 전체 한도는 그대로 남는다.
  2. 한도 세기는 프로세스 하나를 전제한다. routing_server.py가 uvicorn을 workers 인자 없이 단일 프로세스로 띄우는 지금은 파일 하나로 충분하지만, 나중에 여러 프로세스로 늘리면 세기를 공용 저장소로 옮겨야 한다.
  3. 모델이 근거 형식을 항상 지키지는 않는다. 근거: [1] [3] 형식을 안 지키면 검색 1~3순위를 대신 붙이는 것으로 보완하지만, 완벽한 일치는 아니다.
  4. 무료 등급에는 가동률 약속이 없다. Google 쪽이 붐비면(429/503) "잠깐 붐빕니다"로 안내하는 것 말고는 할 수 있는 일이 없다.
